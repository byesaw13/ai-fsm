## Problem Statement

Each kind of job comes in many variants: a dimmer is single-pole, 3-way or 4-way; a toilet may need a
new supply line and shut-off; a bath fan may need a roof cap or a wall hood. The buy list today does
not ask about these choices. So parts get missed, and a missed part means a second trip to the store
in the middle of the job: downtime that is never billed.

The owner wants the system to ask the questions a careful estimator asks for each job ("do you need
this? which type? which kind? any accessories?") so nothing is overlooked when purchasing.

## Demand Evidence

- Owner, 2026-08-07: "I spend a lot of time 3 to 8 hours alone trying to figure out the materials list
  and I am still running to the supply house over and over because of not enough product or not
  having it at all."
- Owner, 2026-10-29: the system should be "smart enough to ask the questions so that it's not missed
  when purchasing for the job and creating downtime to go get it."

Nothing today asks **which variant** or **which accessories**. Kits are fixed lists, so a 3-way
dimmer job gets the same list as a single-pole one.

## How estimators already solve this (landscape)

- **Assemblies with questions.** Commercial estimating tools build a job type as an "assembly" that
  asks the estimator questions at takeoff and picks items from the answers. Sage Estimating lets an
  assembly hold items that are chosen at takeoff, with a default selection. Destini Estimator
  answers "assembly questions" and marks which ones still need a value.
- **Companion-item suggestions.** Xactimate suggests items that are commonly paired with the line you
  just added, and on mobile tailors this by trade, room and loss type. Its AI line-item advisor
  explicitly does **not** produce a complete list for a job, so suggestions supplement a checklist,
  never replace it.
- **Pre-departure checklists.** Handyman operators recommend confirming materials, what the client is
  supplying, and scope before leaving; electricians report that a mid-job supply run disrupts the
  work more than ordering ahead.
- **Takeaway (conventional wisdom holds):** a written per-job-type question list, with defaults, is
  the proven pattern. AI helps by pre-answering from the scope and by drafting lists for rare jobs.

Sources: Sage Estimating help (assembly takeoff), Beck Technology Destini Estimator 2022.2 feature
list, Xactware help (suggested items), Verisk Xactimate platform comparison, Bulletproof Handyman

## Premises (agreed 2026-10-29)

1. The goal is **no second store trip**, not a better price.
2. Build on the existing job buy list and per-code kits, not a new AI chat surface.
3. Each job type gets a short **written checklist of questions**. The AI fills in answers it can tell
   from the scope and asks the owner the rest. Once a checklist is approved, the AI never adds parts
   outside it. (Drafting a checklist for a rare job, below, is the one place the AI proposes parts,
   and nothing it drafts is used until the owner approves it.)
4. Start with the 15 to 20 jobs done most, not all 115 codes.
5. (Added by the owner) Jobs done rarely still get a checklist: the AI drafts one the first time, the
   owner approves it, and the approved version is saved to that code.

## Approaches Considered

- **A: written checklists only, no AI.** Ruled out: rare jobs get nothing.
- **B: checklists + AI fill-in + AI drafts for rare jobs.** Chosen.
- **C: B plus a "what did we forget?" log.** Deferred to its own later design: it needs months of

## Recommended Approach

### What a checklist is

A checklist belongs to one price book code. It is a short list of questions. Each question has:

- **prompt**: "Which kind of dimmer?"
- **kind**: yes/no, pick one, or a number (for example duct length in feet)
- **choices**, each naming the kit rows it turns on, for example
  `3-way → "Dimmer, 3-way, 600 W" ×1`. One model only: a choice **selects** kit rows; it never
  edits or swaps them. A "number" answer feeds the existing `dimensions` / `input_key` quantity path.
- **default**: the usual answer, so a quick job takes one tap
- **when**: an optional condition, limited to "an earlier answer on this checklist equals X"
  ("only if: replacing an existing fan = yes")
- **why** (optional): the reason the question exists ("old fans often have 3-inch duct; new ones
  need 4-inch")

Example, code 3005 (dimmer switch):

| Question | Choices → adds to buy list |
|---|---|
| Which kind? | single-pole (default) / 3-way / 4-way → that dimmer |
| What load? | LED (default) / incandescent / fan → LED-rated or fan-speed control |
| Smart or standard? | standard (default) / smart → smart dimmer; asks "neutral wire in the box?" |
| Neutral wire in the box? (only if smart = yes) | yes / no → no-neutral smart model |
| New wallplate? | yes (default) / no → decorator wallplate |
| Box crowded or old wiring? | no (default) / yes → deep box, wire nuts, pigtail |

Each question must be able to cause a wrong or missing part. Color and style are left to a free-text
note on the line, not a question, because they rarely send anyone back to the store.

Questions that change **hours** (fan with light vs. fan only) stay on the estimate side, the way
Craftsman separates them. Questions that only change **the part** live in the checklist.

### Data model (sketch, additive)

- `price_book_checklists`: `id`, `price_book_id`, `version` (int), `status` (`draft` | `approved`),
  `questions` (jsonb array of {key, prompt, kind, choices[{key, label}], default, when, why,
  input_key}; `input_key` is set only on number questions and names the `dimensions` key it fills),
  `approved_by`, `approved_at`. One approved version is current per code; editing creates a new
  version.
- `price_book_template_choices` (join table): `template_id` → `price_book_material_templates.id`,
  `question_key`, `choice_key`. A kit row with no join rows behaves exactly as today, so the 5
  existing kits keep working unchanged. A row with join rows is included when **any** of its choices
  was picked (so wire nuts can serve both "3-way" and "crowded box"). A join table, not a column, so
  the existing unique index `uq_pbmt_task_name` stays as is. Tests pin all three cases.
- **Hidden questions** (their `when` is false) select nothing. Their defaults are ignored.
- `checklist_answers`: `estimate_line_item_id`, `job_id` (null until the job exists),
  `price_book_code`, `instance` (1, 2, 3… for each unit of the work, so 3 dimmers can be 2
  single-pole and 1 3-way), `checklist_id` + `version` (snapshot, so a later edit to the checklist
  never changes an answered job), `answers` (jsonb), `source` per answer
  (`default` | `inferred` | `owner`). Answers are made on the estimate. When the job is created from
  the estimate (`job-from-estimate.ts`), `job_id` is filled in. A job with no estimate answers on the
  job directly (`estimate_line_item_id` null).
- `job_material_lines` gains `checklist_answer_id` (nullable), so each kit line knows which instance
  it came from.
- Build expands **once per instance**, with that instance's own number answers as `dimensions`. Lines
  for the same part across instances are then summed into one buy-list line per part, keeping a link
  to each instance (today's name+unit de-dupe would otherwise drop repeats).
- Template tables have no `account_id` today (single tenant; owner/admin writes only through RLS).
  Checklists follow the same rule. Noted as a known limit, not a change.

### How an item finds its checklist

Checklists are keyed by price book code. Estimate lines carry `price_book_id`, but in prod it is
**rarely filled in (0 of 84 lines, 2026-10-29)**. So v1 sets it wherever the line is created from the
price book (Prepare Quote, AI items, the price book picker). A free-text line with no code gets no
checklist; the buy list shows it as "no checklist: add a code or add parts by hand".

### Where it runs

1. **On the estimate** (Prepare Quote): once the work items and their codes are known, the system
   runs each item's checklist. Pre-filling is one call to the existing AI path (same model and key
   guard as `materials-generator.ts`). It returns an answer only when the assessment or description
   states it; anything uncertain is left blank, never guessed. Pre-filled answers are labeled
   "from your notes". The rest are asked, one screen per work item, with defaults selected.
2. **On the job buy list**: the build step (`materials/build`) reads the answers and expands only the
   kit rows they select (via `expandMaterialTemplatesDetailed`).
3. **Changing an answer** after the buy list exists: lines that came from that instance's checklist
   (`generation_source = 'template'`, matching `checklist_answer_id`) with status `needed` are
   removed and rebuilt from the new answers. Lines with status `purchased` or `on_truck` are kept and
   flagged "answer changed after purchase"; `not_needed` lines stay as they are. Hand-added lines are
   never touched.
4. **Before the store run**: the job's buy list page (`/app/jobs/[id]/materials`) shows any blank
   question as "Still to decide" at the top. (A multi-job day view is out of scope; it was deferred in
   the 2026-08-04 design.) The build route is owner/admin only today, so this step is too.

### Rare jobs: AI-drafted checklists

When a code with no checklist is used, the AI drafts one. In v1 it drafts only from the owner's own
catalog, receipts and job notes. The Craftsman reference (TASK-218) is **not** sent to the AI: the
ROADMAP says it never feeds AI. Instead, the code's Craftsman lines and "includes" text are shown to
the owner beside the draft, and the owner adds what they list by hand. Using Craftsman as an AI input
would need an owner-approved change to the TASK-218 ROADMAP bullet first.
Manufacturer guides and code reminders are later inputs. The draft is saved with status `draft`, the
owner edits it on that job, and approving it makes it the code's current version. Next time, the
approved version is used and the AI does not redraft it.

### Later (not in this design): "what did we forget?" log

Logging lines added after the store run, and receipt lines that weren't on the list, then suggesting
new questions from repeated misses. This needs receipt-to-list matching, which is its own project. It
gets a separate backlog note once checklists exist.

### Sources for checklist content

| Source | Gives | Limit |
|---|---|---|
| Craftsman (owner subscription) | Variant names (types, sizes, grades), what each line includes | Owner reads it while writing checklists; never an AI input (ROADMAP); no store SKUs; no bulk import |
| Owner's receipts and catalog (1,304 items) | The actual parts bought, with SKUs and prices | Only covers what has been bought before |
| Manufacturer install guides (later) | "You will need" accessory lists | One product at a time |
| Electrical and plumbing code (later) | Required items (for example GFCI or tamper-resistant devices where required) | A reminder, not a code-compliance check |
| The owner's own misses (later log) | The questions that actually get overlooked | Needs months of data |

## Success Criteria

- For a job built from checklists, no unplanned store trip for a missing or wrong part. Until the
  later log exists, the owner notes misses on the job; the first month sets the baseline.
- A typical checklist takes under 30 seconds when defaults are right.
- Every price book code used in a month has a checklist, approved or still in draft.

## The Assignment

Write down the 15 jobs you did most this year. For three of them (suggest: dimmer or switch, toilet
swap, faucet swap), list every part you have had to go back to the store for. That list is the first
three checklists, and it tests whether the question format captures your real misses.
